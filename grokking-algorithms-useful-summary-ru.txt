===============================================================================
0. ГЛАВНАЯ ИДЕЯ КНИГИ
===============================================================================

Алгоритмы не надо запоминать как коллекцию листингов. Нужно научиться:

1) распознавать форму задачи;
2) выбирать структуру данных;
3) формулировать инвариант — что остаётся истинным на каждом шаге;
4) оценивать время и память;
5) проверять ограничения, на которых держится корректность.

Короткая карта выбора:

  Данные отсортированы? ---------------- да --> бинарный поиск
           |
           нет
           v
  Нужен быстрый поиск по ключу? -------- да --> хеш-таблица
           |
           нет
           v
  Есть вершины и связи? ---------------- да --> граф
           |                                |
           |                                +-- все рёбра равны --> BFS
           |                                +-- веса >= 0 ------> Дейкстра
           |                                +-- зависимости ----> топологическая сортировка
           v
  Есть повторяющиеся подзадачи и выбор? - да --> динамическое программирование
           |
           v
  Можно доказать безопасный локальный
  лучший выбор? ------------------------- да --> жадный алгоритм

Самый полезный вопрос перед кодом:
«Какое свойство входа позволяет не перебирать все варианты?»

===============================================================================
1. BIG O: КАК ДУМАТЬ О РОСТЕ
===============================================================================

Big O описывает, как растёт стоимость алгоритма при росте входа n. Это не время
в миллисекундах и не точное число операций. Обычно обсуждают верхнюю границу
роста, отдельно для времени и дополнительной памяти.

  O(1)        доступ по индексу, lookup в хорошей хеш-таблице в среднем
  O(log n)    бинарный поиск, операции сбалансированного дерева
  O(n)        один полный проход
  O(n log n)  эффективная сортировка сравнением
  O(n^2)      сравнение каждой пары, selection sort
  O(2^n)      перебор подмножеств
  O(n!)       перебор перестановок

Интуиция для n = 1 000 000:

  O(1)       ~ 1 шаг
  O(log2 n)  ~ 20 шагов
  O(n)       ~ 1 000 000 шагов
  O(n^2)     ~ 1 000 000 000 000 шагов

Практические правила:

- Отбрасываем константы и младшие члены: O(3n + 20) = O(n).
- Последовательные независимые части складываются: O(n) + O(m).
- Вложенные полные проходы обычно перемножаются: O(n * m).
- Для рекурсии учитываем глубину стека.
- Average case нельзя выдавать за worst case.
- O(1) lookup хеш-таблицы — ожидаемая, а не безусловная гарантия.
- При малых n простое решение иногда быстрее сложного «асимптотически лучшего».

На собеседовании всегда проговори:
«Время O(...), дополнительная память O(...), где n — ...»

===============================================================================
2. МАССИВЫ И СВЯЗНЫЕ СПИСКИ
===============================================================================

Массив хранит элементы подряд. Это даёт быстрый произвольный доступ и хорошую
локальность данных для CPU-кэша.

  индекс:     0      1      2      3
            +------+------+------+------+
  массив:   |  A   |  B   |  C   |  D   |
            +------+------+------+------+

Связный список хранит узлы и ссылки:

  [A | *] --> [B | *] --> [C | *] --> null

                           Массив       Связный список
  Доступ по индексу        O(1)         O(n)
  Поиск по значению        O(n)         O(n)
  Вставка в середину       O(n)         O(1), если узел уже найден
  Удаление                 O(n)         O(1), если узел/предок уже найден

Главная оговорка: «вставка в список O(1)» бесполезна, если сначала надо O(n)
искать место вставки. В прикладном коде динамический массив/List<T> часто лучше
списка из-за локальности памяти, меньшего overhead и удобства обхода.

Selection sort полезен как учебный контраст: на каждой позиции ищем минимум
среди оставшихся элементов. Время O(n^2), память O(1). В production почти всегда
следует использовать стандартную библиотечную сортировку.

===============================================================================
3. БИНАРНЫЙ ПОИСК
===============================================================================

Применим, когда область поиска упорядочена или ответ обладает монотонностью.
На каждом шаге отбрасывается половина вариантов.

  [ 1  4  7  9  12  18  25 ]    ищем 18
              ^ mid=9
                 18 > 9, левую половину отбрасываем
                 [ 12  18  25 ]
                       ^ найдено

Время O(log n), память O(1) в итеративной реализации.

Надёжный шаблон поиска точного значения:

  left = 0, right = n - 1
  пока left <= right:
      mid = left + (right - left) / 2
      если a[mid] == target: вернуть mid
      если a[mid] < target:  left = mid + 1
      иначе:                 right = mid - 1
  вернуть «не найдено»

Инвариант: если target существует, он находится внутри [left, right].

Типовые ошибки:

- поиск по неотсортированным данным;
- путаница между закрытым [left, right] и полуоткрытым [left, right) интервалом;
- left = mid вместо mid + 1, что создаёт бесконечный цикл;
- неверная обработка дублей;
- поиск «первого подходящего» без сохранения кандидата.

Более сильный паттерн — binary search on answer. Если predicate(x) меняется только
один раз, например F F F T T T, можно найти первую T за O(log range):

  невозможные ответы             возможные ответы
  F   F   F   F   |   T   T   T   T
                  граница ^

Примеры: минимальная вместимость, при которой укладываемся в срок; максимальная
скорость/нагрузка, ещё удовлетворяющая ограничению.

===============================================================================
4. РЕКУРСИЯ, СТЕК И «РАЗДЕЛЯЙ И ВЛАСТВУЙ»
===============================================================================

У рекурсивного решения обязательно есть:

- base case — простой случай, который завершает рекурсию;
- recursive case — переход к меньшей версии задачи;
- доказательство прогресса — аргумент действительно приближается к base case.

  fact(4)
    -> 4 * fact(3)
             -> 3 * fact(2)
                      -> 2 * fact(1)
                               -> 1

Стек вызовов хранит параметры, локальные переменные и адрес возврата. Глубокая
рекурсия расходует O(depth) памяти и может привести к StackOverflowException.
Для потенциально очень глубоких деревьев/графов лучше явный Stack<T>.

Divide and conquer:

1) определить простой базовый случай;
2) разделить задачу на меньшие части;
3) решить части;
4) объединить результаты.

Quicksort:

  [ 9  3  7  1  5 ]   pivot=5
         /                  \
    [3 1] < 5             [9 7] > 5
       sort       + 5 +      sort
       [1 3]                 [7 9]
  результат: [1 3 5 7 9]

Среднее время quicksort O(n log n), худшее O(n^2), стек в среднем O(log n).
Плохой pivot и уже упорядоченный вход могут давать крайне несбалансированные
части. Случайный pivot или introsort уменьшают риск. Quicksort обычно нестабилен.

Главная ценность главы — не реализация сортировки, а декомпозиция задачи и анализ
того, сколько уровней разбиения и сколько работы выполняется на каждом уровне.

===============================================================================
5. ХЕШ-ТАБЛИЦЫ
===============================================================================

Хеш-функция переводит ключ в позицию. Коллизии неизбежны: разные ключи иногда
попадают в один bucket, поэтому нужна стратегия их разрешения.

  key ----hash----> bucket
  "user:42" ------> [42] --> (key,value) --> (другая коллизия)

Ожидаемые операции lookup/insert/delete: O(1). Худший случай: O(n).

Хеш-таблица особенно полезна для:

- отображения key -> value;
- множества уже виденных значений;
- счётчиков частот;
- кэширования;
- удаления повторной работы;
- преобразования двух проходов/вложенного цикла в один проход.

Ключевой паттерн:

  seen = пустое множество
  для x во входе:
      если complement(x) уже в seen: решение найдено
      добавить x в seen

Обычно это меняет brute force O(n^2) на O(n) времени ценой O(n) памяти.

Production-оговорки:

- Ключ должен иметь корректные и согласованные equality/hash semantics.
- Изменяемый ключ после вставки ломает поиск.
- Рост таблицы и rehash дают редкие, но дорогие операции.
- HashMap не сохраняет сортированный порядок, если контракт явно этого не обещает.
- Для враждебного ввода важны защита от hash-flooding и лимиты памяти.

===============================================================================
6. ГРАФЫ И BFS
===============================================================================

Граф состоит из вершин V и рёбер E. Сначала нужно правильно смоделировать:

- направленные или ненаправленные связи;
- взвешенные или невзвешенные рёбра;
- возможны ли циклы;
- нужен сам факт достижимости, кратчайший путь или порядок зависимостей.

Список смежности обычно хранит разреженный граф за O(V + E) памяти:

  A: B, C
  B: D
  C: D, E
  D: -
  E: -

BFS идёт слоями и использует FIFO-очередь:

             A                 distance 0
          /     \
         B       C             distance 1
         |     /   \
         D    D     E          distance 2

  queue: [A] -> [B,C] -> [C,D] -> [D,E] -> ...

BFS даёт кратчайший путь по числу рёбер только в невзвешенном графе (или когда
все рёбра имеют одинаковую стоимость). Время O(V + E), память O(V).

Критически важно помечать вершину visited при добавлении в очередь, а не после
извлечения: иначе одну вершину могут многократно поставить в очередь.

Для восстановления пути хранить parent[next] = current:

  start <- ... <- parent[parent[target]] <- parent[target] <- target

DFS использует стек/рекурсию и идёт в глубину. Он удобен для обхода дерева,
компонент связности, поиска циклов, backtracking. Но первый найденный DFS-путь
не обязан быть кратчайшим.

Топологическая сортировка применима только к DAG. Она строит порядок, в котором
каждая зависимость идёт раньше зависящего от неё узла. Если обработать все вершины
невозможно, в графе есть цикл.

===============================================================================
7. ДЕРЕВЬЯ, BST И B-TREE
===============================================================================

Дерево — связный ациклический граф. В корневом дереве у каждого узла, кроме
корня, один родитель.

             8
           /   \
          3     12
         / \    / \
        1   6  10  14

В binary search tree (BST) значения слева меньше, справа больше. Поиск, вставка
и удаление занимают O(height):

- сбалансированное дерево: height = O(log n);
- вырожденное дерево: height = O(n), фактически связный список.

Балансировка нужна не для красоты, а для ограничения высоты. B-tree/B+tree имеют
много потомков на узел, уменьшая число обращений к страницам; поэтому их семейство
широко применяется в индексах БД и файловых системах. Реальный индекс БД сложнее
учебного BST: имеют значение страницы, cache, fill factor, конкурентные записи,
селективность и порядок колонок.

Три полезные модели из расширенной главы второго издания:

- AVL-tree строго ограничивает разницу высот поддеревьев и после обновлений делает
  повороты. Поиск/вставка/удаление O(log n), но обновления платят за балансировку.
- Splay-tree поднимает недавно использованный узел к корню. Отдельная операция
  может быть O(n), зато амортизированная стоимость O(log n), а «горячие» ключи
  естественно оказываются ближе.
- B-tree держит много ключей в одном узле. Низкая высота минимизирует дорогие
  обращения к страницам. Это пример того, почему реальная стоимость CPU cache/I/O
  иногда важнее абстрактного числа сравнений.

Huffman coding строит префиксное дерево: частые символы получают короткие коды,
редкие — длинные. Главный переносимый урок: структура данных может кодировать
ограничение так, что декодирование становится однозначным без разделителей.

===============================================================================
8. АЛГОРИТМ ДЕЙКСТРЫ
===============================================================================

Находит кратчайшие расстояния от одной стартовой вершины в графе с
НЕОТРИЦАТЕЛЬНЫМИ весами.

  A --4--> B
  |        |
  1        1
  v        v
  C --2--> D

Идея relaxation:

  если dist[u] + weight(u,v) < dist[v],
      обновить dist[v] и parent[v]

Алгоритм всегда выбирает необработанную вершину с минимальным известным dist.
С priority queue: O((V + E) log V), память O(V + E).

Инвариант: когда вершина извлечена как минимальная, более короткий путь к ней уже
не появится — это верно именно из-за отсутствия отрицательных рёбер.

Если есть отрицательные веса, нужен другой алгоритм, например Bellman–Ford.
Если все веса одинаковы, BFS проще и дешевле.

Типовая реализационная деталь: priority queue может содержать устаревшие записи.
При извлечении записи с distance больше актуального dist[node] её пропускают.

===============================================================================
9. ЖАДНЫЕ АЛГОРИТМЫ И NP-ТРУДНЫЕ ЗАДАЧИ
===============================================================================

Жадный алгоритм на каждом шаге делает локально лучший выбор и не пересматривает
его. Это не универсальный метод. Нужны доказуемые свойства задачи.

Пример интервального планирования: чтобы выбрать максимум непересекающихся
интервалов, сортируем по времени окончания и каждый раз берём первый совместимый.

  время --->
  A: [------]
  B:    [--]       берём B: он раньше освобождает ресурс
  C:       [---]   затем берём C

Почему «самый дорогой предмет первым» не решает 0/1 knapsack: локально выгодный
предмет может заблокировать комбинацию с большей общей ценностью.

Признаки потенциально трудной комбинаторной задачи:

- требуется оптимум среди всех подмножеств/перестановок;
- небольшое изменение условия разрушает известное простое решение;
- точный алгоритм растёт экспоненциально;
- задача похожа на set cover, traveling salesperson, 0/1 knapsack.

В production часто правильный ответ — не «найти идеальный оптимум», а определить:

- допустима ли аппроксимация;
- какой нужен предел времени/памяти;
- можно ли ограничить размер входа;
- можно ли применить heuristic, branch-and-bound или offline-расчёт;
- как измерить качество приближения.

===============================================================================
10. ДИНАМИЧЕСКОЕ ПРОГРАММИРОВАНИЕ (DP)
===============================================================================

DP применимо, когда:

1) задача раскладывается на перекрывающиеся подзадачи;
2) оптимальный ответ строится из оптимальных ответов подзадач;
3) состояние содержит всю информацию, нужную для будущих решений.

Brute force повторяет одинаковую работу:

                 F(5)
              /        \
           F(4)        F(3)
          /   \        /   \
       F(3)  F(2)   F(2)  F(1)
       ^ повторяется ^

Memoization (top-down) кэширует результаты рекурсивных вызовов.
Tabulation (bottom-up) заполняет таблицу от простых состояний к сложным.

Пять шагов проектирования DP:

1) State: что однозначно описывает подзадачу?
2) Transition: из каких меньших состояний получается текущее?
3) Base cases: какие ответы известны сразу?
4) Order: в каком порядке зависимости уже вычислены?
5) Answer: в какой ячейке/агрегации находится результат?

Сложность обычно:

  количество состояний * число переходов на состояние.

Для 0/1 knapsack:

  dp[i][capacity] = максимум ценности, используя первые i предметов.

  не брать предмет i: dp[i-1][capacity]
  взять предмет i:    value[i] + dp[i-1][capacity-weight[i]]

Здесь сложность O(items * capacity), память O(items * capacity), часто сжимается
до O(capacity). При сжатии 0/1 knapsack capacity обходят справа налево, иначе один
предмет случайно используется несколько раз.

Для longest common substring состояние можно определить так:

  dp[i][j] = длина общей ПОДСТРОКИ, заканчивающейся в a[i-1] и b[j-1].

Если символы равны, dp[i][j] = dp[i-1][j-1] + 1; иначе 0. Максимум по таблице —
ответ. Не путать с longest common subsequence: подстрока обязана быть непрерывной,
подпоследовательность — нет. Для строк длины m и n время O(m*n), память O(m*n),
которую можно сократить до O(min(m,n)).

Главная ошибка — начать рисовать таблицу до определения точного смысла ячейки.
Фраза «dp[i] — лучший ответ до i» обычно недостаточна: лучший по какому критерию,
при каких ограничениях и включается ли i?

===============================================================================
11. K-NEAREST NEIGHBORS (KNN)
===============================================================================

KNN классифицирует объект по ближайшим размеченным примерам; для регрессии можно
усреднять значения соседей.

  x x x                 o o
   x x      ?         o o o
           ближайшие точки определяют класс ?

Евклидово расстояние — лишь один вариант. Качество зависит от:

- выбора признаков;
- масштабирования: признак с большими числами иначе доминирует;
- выбора k;
- метрики расстояния;
- шума, выбросов и дисбаланса классов;
- «проклятия размерности»: в высокой размерности близость теряет смысл.

Наивный запрос требует O(n * d), где n — число примеров, d — число признаков;
хранение O(n * d). KNN прост и объясним, но дорог на больших наборах и не заменяет
полноценную процедуру обучения/валидации модели.

Quicksort                       avg O(n log n), worst O(n^2)  стек avg O(log n)
Hash lookup                     avg O(1), worst O(n)          O(n)
BFS / DFS                       O(V + E)                      O(V)
BST operation                   O(height)                     balance важен
Dijkstra + heap                 O((V + E) log V)              веса >= 0
0/1 knapsack DP                 O(n * capacity)               O(n*C) или O(C)
KNN query                       O(n * d)                      хранит набор O(n*d)

13. КАК ОБЪЯСНЯТЬ РЕШЕНИЕ НА СОБЕСЕДОВАНИИ
===============================================================================

Не начинай с кода. Используй порядок:

1) Requirements
   «Правильно ли я понял: ...? Каковы ограничения n? Возможны ли дубли/пустой ввод?»

2) Assumptions
   «Массив отсортирован», «веса неотрицательны», «граф может иметь циклы».

3) Baseline
   Коротко назови brute force и его сложность. Это показывает, что оптимизация
   осознанна, а не угадана.

4) Ключевая идея и структура данных
   «Хеш-множество хранит уже виденные значения» или «очередь обеспечивает обход
   по слоям».

5) Инвариант
   «До текущей позиции minPrice — минимум на префиксе; bestProfit — лучший ответ
   среди уже просмотренных дней».

6) Complexity
   Отдельно time и extra space; определить n/V/E.

7) Edge cases
   Пустой/единичный ввод, дубли, переполнение, цикл, недостижимая вершина,
   отрицательный вес, очень глубокая рекурсия.

8) Predicted result и tests
   До запуска кода предскажи результат для normal, boundary и adversarial cases.

Мини-шаблон ответа:

«Brute force сравнивает все пары за O(n^2). Я могу хранить ... в HashSet. При
обработке x проверяю ..., затем добавляю x. Инвариант: set содержит ровно элементы
префикса до текущей позиции. Поэтому ... . Один проход даёт O(n) времени и O(n)
дополнительной памяти. Проверю пустой ввод, дубли и ...»

14. ЧЕГО КНИГА НЕ ЗАКРЫВАЕТ ПОЛНОСТЬЮ
===============================================================================

Книга отлично создаёт интуицию, но одной её недостаточно для алгоритмического
собеседования Middle+/Senior. Нужно отдельно тренировать:

- two pointers;
- sliding window;
- prefix sums;
- stack/monotonic stack;
- heap/priority queue;
- интервалы;
- lower_bound/upper_bound и бинарный поиск по ответу;
- topological sort и union-find;
- backtracking;
- системное проектирование DP-state;
- доказательство корректности и восстановление ответа;
- C#-специфику коллекций и PriorityQueue<TElement,TPriority>.

Рекомендуемый порядок практики:

1) arrays/strings + hashing;
2) two pointers, sliding window, prefix sums;
3) stack/queue и binary search;
4) linked lists и intervals;
5) trees: DFS/BFS;
6) graphs, topological sort, shortest paths;
7) dynamic programming после устойчивых fundamentals.

15. ЧЕК-ЛИСТ «Я ДЕЙСТВИТЕЛЬНО ПОНЯЛ»
===============================================================================

Для каждого алгоритма ответь без подсказки:

[ ] Какую форму задачи он распознаёт?
[ ] Какие preconditions обязательны?
[ ] Какая структура данных обеспечивает нужный порядок работы?
[ ] Какой инвариант доказывает корректность?
[ ] Каковы time и extra space complexity?
[ ] Как выглядит худший случай?
[ ] На каком counterexample алгоритм ломается?
[ ] Как восстановить не только стоимость, но и сам путь/набор решений?
[ ] Когда библиотечная реализация лучше собственной?
[ ] Могу ли я написать решение и три теста за 20–30 минут?

Если можешь только узнать алгоритм по названию, это recognition, а не владение.
Владение подтверждается новым заданием без подсказки и повторной проверкой через
несколько дней.
